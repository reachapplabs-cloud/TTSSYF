1 · Push Notifications, Admin → Buyer

Scope‑freeze needed

Two trigger types, both in scope, both landing as a push to the buyer: manual (admin composes and sends to a chosen segment) and automated (the system fires on a defined event — order state, idle cart, stock/ price change — no human per send). They share one delivery pipeline and one set of guardrails; what differs is who or what starts the send.

Trigger type A · Manual

Admin composes and sends/schedules from the admin panel to a chosen segment.

1Business decides to run a saleAll buyers, or region-specific"Independence Day Sale — flat 30% off, today only."
2New seller/category goes liveBuyers with browse/purchase history in that category"New arrivals from [Seller] just landed."

4Seller needs to clear inventoryBuyers who viewed/wishlisted that category"Clearance on [Category] — up to 50% off, limited stock."
5Platform feature/policy updateAll buyers"New: track your order in real time."

Audience targeting ("selected user base")

Proposed v1 segments — confirm/trim before scoping:

  • All buyers
  • Buyers in a location / city / region
  • Buyers who've purchased from a given seller or category before
  • Buyers with items in cart or wishlist, no recent purchase
  • New signups in the last N days
  • Inactive buyers (no activity in last N days)

Ship a usable subset (e.g. location + category/seller + all-buyers) rather than blocking v1 on every segment being possible.

Trigger type B · Automated

System-fired on a defined event, no manual send required.

Nine candidate triggers is too many to build at once. Suggested v1 priority: order status (#4), abandoned cart (#1), back-in-stock (#2) — highest value, likely least new plumbing since order state is already core to the app. The rest are reasonable fast-follows once the trigger pipeline exists.

Shared mechanics (both types)

  • Same delivery pipeline: title/body/image/deep link, mobile push.
  • Automated triggers need an event pipeline wired to real system events (order state, cart state, wishlist state, stock level) — the actual cost driver, see open questions.
  • Admin needs one unified history/log covering manual sends and automated fires together, plus a per-trigger on/off toggle for automated ones.
  • Per-trigger message templates need variables (e.g. {item_name}, {order_id}) rather than hardcoded copy.

Message content

  • Title + body text, optional image
  • Optional deep link — to a product, category, seller, or in-app screen
  • Manual: send now or schedule for later. Automated: fires on the event, with a configurable delay (e.g. cart abandonment "X hours").

Guardrails

  • Combined daily send cap per buyer across manual + automated together — no stacking an abandoned-cart ping with a browse-abandonment ping same day.
  • Dedup/priority rules when multiple automated triggers fire close together (e.g. order-status wins over browse-abandonment).
  • Respect existing opt-out / notification preferences.
  • No sends outside a reasonable local time window.

Admin-side deliverable

  • Manual compose screen: message, image, audience selector, deep link, schedule.
  • Automated trigger config screen: per-trigger on/off, message template with variables, per-trigger condition tuning (e.g. the "X hours" cart threshold).
  • Unified send history/log for both types.
  • Delivery stats — sent, opened, clicked (nice-to-have; can slip to v1.1 if it threatens the freeze deadline)

Out of scope for v1

  • Web push (mobile app push only, unless trivial given existing infra)
  • A/B testing of notification content
  • AI/ML-driven send-time optimization or personalized copy

2 · Widget Bulk Import — Home Screen Performance

Blocking Monday deploy

Needed for Kavish.

Context

  • Original scope assumed 20–25 products per widget.
  • Seller team is now planning 100+ products per widget.
  • Bulk import itself is built and ready.
  • Gap: rendering that volume back on the home screen — Website and mobile — hasn't been performance-checked or optimized.

What's needed

  • Performance test the home screen with widgets carrying 100+ products each, on both Website and mobile.
  • Optimize rendering — candidates to evaluate: pagination/"load more", infinite scroll, or virtualized rendering of the widget's product list; image lazy-loading; response caching.
  • Confirm this covers multiple large widgets stacked on one home screen, not just one widget in isolation.

Expectation on Monday's deploy

Confirm explicitly whether this is:

  • (a) part of Monday's deploy — i.e. Monday slips — or
  • (b) shipped Monday for the 20–25 case as originally scoped, with the 100+ optimization as a fast-follow.

Whichever it is, say so directly — Kavish needs a real date, not an implied one.

Open questions for Vanitha
  1. What's the realistic ceiling to design for — ~100–150, or could sellers push further? Designing for the wrong ceiling wastes effort either way.
  2. Does this affect only the home screen, or do category/search listings pull from the same widget data and need the same fix?
  3. Is this a rendering fix only, or does the bulk-import → home-screen data pipeline itself need changes to support the volume?
