A · Manual notifications (admin composes and sends by hand)

This is the simple case: a person on the admin side writes a message and sends it to a group of buyers they pick. Nothing automatic here.

What the admin enters when composing a message

  • A title — the short bold headline of the push notification.
  • A body — the longer message text underneath the title.
  • Optionally, an image attached to the notification.
  • Optionally, a deep link — tapping the notification opens directly to a specific product, category, or seller page, or another specific screen in the app, instead of just opening to the home screen.
  • A choice of "send immediately" or "schedule for a specific future date and time."

Who the message goes to (admin picks one group)

  • Every buyer on the platform.
  • Buyers located in a specific city or region.
  • Buyers who've previously bought from a specific seller, or bought in a specific category before (e.g. "everyone who's bought electronics").
  • Buyers who currently have something in their cart or wishlist but haven't purchased recently.
  • Buyers who signed up within the last N days (a "new users" group).
  • Buyers who haven't opened the app or done anything on it in the last N days (an "inactive users" group).

A record of what was sent

Every manual message that goes out is logged: what it said, which group it went to, and when it was sent, so it can be looked back on later.

Limits on manual sending

A cap on how many notifications one buyer can receive in a single day; the system respects it if a buyer has turned off notifications; and messages aren't sent late at night or early morning in the buyer's local time.

B · Automated notifications (the system sends these on its own)

These go out automatically the moment something specific happens in the app — the admin doesn't write or click send for each one; they turn the feature on once, and the system handles it from then on for every buyer it applies to.

1Order status change

Every time an order moves to a new stage — placed, shipped, out for delivery, delivered, cancelled, or refunded — the buyer who placed that specific order automatically gets a notification saying so. The moment an order is marked "shipped" in the system, that buyer gets "Your order has shipped" without anyone sending it by hand.

2Abandoned cart

If a buyer adds something to their cart and doesn't complete checkout within a set number of hours (a number we choose — e.g. 6 or 24), the system automatically sends that one buyer a reminder about the item still in their cart.

3Wishlist-to-cart follow-through

A more specific version of the above: if a buyer had something in their wishlist, then moved it into their cart, but still hasn't bought it after a set number of hours, they get a reminder calling that out specifically — it's a stronger signal of intent than a random cart item.

4Back-in-stock

If a product was out of stock and a buyer had wishlisted it, the moment that product becomes available again, every buyer who wishlisted it automatically gets notified it's back.

The admin screen needed to control those four

One settings page in the admin panel, with each of the four triggers listed as its own row. For each row, the admin needs to do three separate things:

Turn it on or off. A switch per trigger. For example, the admin could switch off "abandoned cart" reminders during a big sale event — so people aren't nagged about carts they're about to buy from anyway — while leaving "order status" notifications running as normal. Each trigger is switched independently; turning one off doesn't affect the others.

Edit the wording of the message, without needing a developer. Right now, if "Your order has shipped" is hardcoded into the app, changing that wording later means asking a developer to change code and redeploy. Instead, the admin panel should let someone type the message directly, with placeholders the system fills in automatically per buyer.

Example: the admin writes the template Your order {order_id} has shipped, and the system replaces {order_id} with the buyer's real order number — "Your order #48213 has shipped" — when it actually sends it. Same idea for back-in-stock: the admin writes {item_name} is back in stock, and the system fills in the real product name for each buyer who receives it.

Adjust the timing that decides when it fires. For abandoned-cart and wishlist-to-cart specifically, "how many hours of inactivity counts as abandoned" shouldn't be a fixed number buried in code — the admin should be able to change it from a settings field (e.g. from 6 hours to 12) if the timing isn't working well, without needing a developer to make a code change.

One combined record of everything sent, manual and automated together

The manual messages already have their own log. The automated ones need to show up in that same log, not a separate one. So looking at the notification history shows one single chronological list that includes both:

"Sale announcement — sent to all Chennai buyers — by admin — 2:00pm"
sitting right alongside
"Order #48213 shipped — sent to buyer X — automated — 2:15pm"

The reason this matters: with two separate logs, checking "what has this buyer received recently" or "did we send too much yesterday" means checking two different places every time. One combined log means one place to look.

Limits so a buyer doesn't get too many messages

The daily cap is shared between manual and automated, not counted separately

Say we decide a buyer should get at most 3 notifications in one day. If a buyer already received 2 automated ones today — their order shipped, and something they wishlisted came back in stock — and then an admin sends a manual sale announcement to everyone, that buyer is already at 2 of their 3 for the day. The manual send counts against the same limit — it isn't a separate "manual bucket."

If they're already at their cap of 3, the system needs to either skip that buyer for the new message or hold it until the next day (the exact behavior is a build decision) — the key point is the cap counts both kinds of message together, not one cap for manual and a separate cap for automated.

When two automated triggers would fire for the same buyer around the same time, one needs to win

Example: a buyer abandons a cart (triggering the abandoned-cart reminder) the same day one of their orders gets marked delivered (triggering the order-status notification). If sending both would push the buyer over their daily cap, or we simply don't want to send two things back-to-back, the order-status notification should be the one that actually goes out, and the cart reminder should be the one skipped or delayed.

Why: order status is about something the buyer already paid for and is waiting on; a cart reminder is closer to a marketing nudge. So the priority order, highest to lowest, is order status first, then the cart-related nudges (abandoned cart, wishlist-to-cart) after.

Phase 2

Fast Follow

next up

Three more automated triggers, same pattern as the four above — each gets its own on/off toggle, an editable message template, and a place in the same unified log and shared daily cap.

Price drop

If the price of something in a buyer's cart or wishlist goes down, that buyer is notified of the new lower price.

Payment failed

If a buyer's payment doesn't go through at checkout, they get a nudge to try again and complete the order.

Low-stock urgency

If something in a buyer's cart or wishlist drops to a low quantity left in inventory (e.g. "only 2 left"), that buyer is notified to create urgency before it sells out.

Delivery analytics

On top of the send log, start tracking whether each notification was actually opened, and whether tapping it led to a click-through (e.g. did the buyer open the product page it linked to). This turns the log from just "what did we send" into "did it actually work" — how many people opened it, how many acted on it.

Phase 3

Backlog

not scheduled

Browse abandonment

If a buyer looks at the same product more than once but never adds it to their cart, after a set number of hours they get a "still interested?" nudge about it.

Post-delivery review reminder

A set number of days after an order is marked delivered, the buyer is asked to leave a review for what they bought.

Inactive-buyer re-engagement

If a buyer hasn't opened the app or done anything on it in a set number of days, they get a "here's what's new" message to try to bring them back.

Web push

Everything above is mobile-app push only for now; sending the same notifications to a buyer's browser is additive work for later, not required for Phase 1–2.

A/B testing of notification content

Sending two different versions of the same message to different buyers to see which performs better — not needed until there's enough volume for it to be worth measuring.

AI/ML-driven send-time optimization or personalized copy

Automatically choosing the best time to send to each individual buyer, or writing personalized message copy per buyer, using a model rather than the fixed rules above — a later refinement once the basic system is working and there's data to learn from.
